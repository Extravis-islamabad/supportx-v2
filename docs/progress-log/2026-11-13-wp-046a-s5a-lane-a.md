## Done

- **Migration 0154.**
  - New columns on `work_item_reply_templates`: `kind`, `subject`, `bodies` (per language),
    `visibility`, `owner_id`, `group_ids` and `category_ids`.
  - The unique name is now per type, kind and owner.
  - A data step runs once per tenant with `app.tenant_id` set and keeps each old text under the
    tenant's default language (an Arabic-first tenant's under `ar`).
  - The downgrade is refused while any tenant uses the new parts (rule 5h).
- **Service (`work_items/service/text_templates.py`).**
  - Personal templates are their owner's only: nobody else lists, reads, fills, changes or
    removes them, administrators included.
  - Shared ones need `config.service_desk` or `settings.manage` to write. Group limits apply to
    offering and filling.
  - Other tenants' group or category IDs are refused, never stored.
  - Variables come from the one notification catalogue (`record_values`). Filling escapes the
    values, an empty one reads "not set", and the result is sanitised again.
  - The language: the screen's choice, then the requester's, then the tenant's default, then
    any the template has.
- **API.**
  - `GET /reply-templates?kind&category_id` and `GET /reply-templates/manage`.
  - POST, PUT and DELETE (audited, If-Match, Idempotency-Key).
  - `POST /{record_id}/reply-templates/{template_id}/fill`.
  - Older clients' single `body` still works.
- **Console.**
  - Admin › Incidents › Reply templates and Resolution templates: language tabs, personal or
    shared, groups, categories, and edit only where `may_edit`.
  - The composer and the resolution editor fill templates on the server for the record.
- **Shared editor (lane C's conditions).**
  - The text goes where the click was, once, and only while the editor is still open.
  - A failed fill inserts nothing (never the raw `{{ variables }}`) and is reported.
  - The empty-menu text now reads "No templates yet" (en, ar, ur).
