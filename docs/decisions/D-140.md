# D-140 (2026-11-05)

## Decision

**Problem management: the product owner's answers to the WP-044 questions** (Haider, through the
coordinator, 2026-11-05; plan ~/Desktop/wp-044-plan.md, file 04).

1. **Closing a problem and its linked incidents** (REQ-PRB-055). The close dialog offers "Resolve
   linked incidents", ticked by default. It copies the resolution to them and notifies their
   requesters, who can still reopen. Incidents are never resolved or closed silently: the person
   closing sees the list and can untick it. Each incident goes through its own service (audited,
   outbox, live). *Changed from the recommendation* (move to resolved, no choice shown).
2. **One problem per incident** (REQ-PRB-043). An incident has at most one problem marked as its
   cause; any others are linked as "related". Built in WP-044a session 3 (a partial unique index;
   409 `incident_has_problem` unless moved).
3. **SLAs on problems** (REQ-PRB-008). Target dates by default, *plus* a tenant switch that
   applies full SLAs (the SLA engine on the problem type) when it is on. *Changed from the
   recommendation* (target dates only).
4. **Problem review** (REQ-PRB-053). Required for major problems and for P1 by default; for P2 it
   is optional, through an admin setting. *Changed from the recommendation* (the major template
   only).
5. **Repeat-incident alerts in Essentials** (REQ-PRB-068). They are shown as an upgrade prompt,
   following the locked-module rule: disabled, with an upgrade hint. The existing admin switch
   that hides upgrade hints hides this one too. The entitlement check stays on the server.
6. **Grouping similar incidents** (REQ-PRB-066). AI groups them wherever the local model runs,
   air-gapped installs included, while AI is on. With AI off it falls back to text similarity
   without AI (pg_trgm, the pattern of D-134). The AI parts go through lane C's gateway.
7. **Root cause visibility** (REQ-PRB-071). Incident technicians see the workaround. By default
   only problem roles see the root cause, which may describe a security weakness, and admins can
   widen that. This is enforced in the API and in search, not only in the UI (the D-052
   agreement).
8. **Mobile** (REQ-PRB-080). The React Native app is V1. It is built by Extravis's separate mobile
   team from their prototype, not by the lanes. The lanes' part is that the public API and push
   notifications cover everything the app needs for problems and incidents (later changes):
   every WP-044 feature is reachable through the public API, with no console-only endpoint.

## Rationale

The product owner chose visible, reversible follow-up over silent changes to incidents (1). He
wants full SLAs available to tenants who run problems to contracts (3), and reviews for the
incidents that hurt most (4). Upgrade prompts follow the one locked-module rule (5). Air-gapped
customers get the same grouping as SaaS (6). Root causes can expose weaknesses, so they are need
to know (7). The mobile app is planned separately, and the API is its contract (8).
