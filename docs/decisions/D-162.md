# D-162 (2026-11-12)

## Decision

**The sign-in session key becomes a rotatable key ring with key IDs** (Haider, the product
owner, through the coordinator; lane B builds it). D-161 left this out and recorded it as
separate lane B work.

1. **A key ring.** The newest key seals new session records; every listed key stays readable
   for an overlap, so a rotation never signs anyone out. Each record moves to the newest key at
   its next save.
2. **Every rotation is audited**, once per key across replicas: a new key and a retired key each
   write one audit entry, IDs and counts only, never key material.
3. **The admin guide documents it**: steps, the overlap (at least the absolute session
   lifetime), what users see (nothing), retiring a key, and the upgrade note on
   `SUPPORTX_API_KEY_SECRET`.
4. **The session secret's other users are untangled**, so a rotation never breaks them: list
   cursors and API-key hashes fall back only to `SUPPORTX_SESSION_SECRET` with today's
   derivations; domain proofs get their own optional `SUPPORTX_DOMAIN_PROOF_SECRET`, falling back
   to the same secret. Production refuses a ring that would leave API keys without their key.
5. **One format for later users** (ADR-048): field encryption (WP-057, lane C) reuses the
   sealed-blob codec and the "who still uses key X" hook.

Settings: `SUPPORTX_SESSION_KEYS` (JSON, newest first, each secret at least 32 characters in
production); `SUPPORTX_SESSION_SECRET` alone stays valid as the one-key ring `legacy`.

## Rationale

- A key with no ID could only be changed by ending every session at once, and the same secret
  also fed cursors, API keys and domain proofs, so changing it broke them too.
- An overlap as long as the longest session means rotation is a routine configuration change.
- Recording key IDs in the database lets several replicas agree that a rotation happened once,
  and lets start-up refuse to drop a key that stored data still needs.
