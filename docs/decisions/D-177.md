# D-177 (2026-11-19)

## Decision

**Single sign-on and directory sign-in never let one account act as another by an e-mail or a
username alone** (Haider, the product owner, through the coordinator).

1. **No v2 installation is live**: only the product owner's local stack, and no tenant has SSO or
   LDAP on in any real installation.
2. **Single sign-on (OIDC and SAML):** an identity provider's sign-in is linked to an account that
   already exists only after the person proves they own it: their existing sign-in, or a
   confirmation sent to the account's own e-mail, then the SSO sign-in. Never on a matching e-mail
   alone.
   - Every tenant identity provider is set not to trust its e-mail (`trustEmail` off), new ones
     when they're saved, and existing ones by the Keycloak identity step (idempotent).
   - A person with no account yet still signs in through the provider as before.
   - The first time an existing account signs in through a provider, it's audited
     (`identity_provider.account_linked`, security, naming the provider).
   - A brokered sign-in already enters only the tenant that owns its provider (#554).
3. **AD/LDAP directory sign-in only on single-tenant installations** (as D-118 already set),
   until per-tenant routing exists.
   - Refused on a multi-tenant installation, with `ldap_single_tenant_only` (en/ar/ur), by the
     integrations service and again by identity_access when writing the directory into Keycloak.
   - The setup page says plainly that a connected directory is asked about any username without
     a SupportX account on the installation.
   - Per-organisation (identity-first) sign-in routing is filed as a work package. The
     real-Keycloak test of the realm-wide lookup stays as a strict xfail until it lands.

## Rationale

Every tenant shares one Keycloak realm (ADR-006), and tenant admins set up their own identity
providers and directories.

- Keycloak 26.8.1 already asks an existing account for proof before linking a provider's person
  to it: re-authentication, or a confirmation to the account's own address when mail is set up.
  Tested with real Keycloak, where the account's secret differs from the provider person's. An
  early test that reported a link on e-mail alone had given both the same password; it was
  wrong and was withdrawn. From now on a security finding stays "suspected" until a second
  lane re-checks its proof (distinct credentials, a negative control that should fail).
- D-177 makes "never on e-mail alone" explicit (`trustEmail` off, kept by the identity step),
  guards it with that real-Keycloak test, and audits the first link. It costs admins nothing:
  each existing person confirms once.
- A directory is a realm-wide component that Keycloak consults for any unknown username (shown
  with real Keycloak and OpenLDAP).
- Keeping directories to single-tenant installations closes the second until a sign-in can be
  routed to its tenant before any directory sees it.
