# D-107 (2026-10-28)

## Decision

**WP-020f defaults** (plan ~/Desktop/wp-020f-plan.md, approved 2026-10-28; **defaults approved 2026-10-28 with two changes**, marked below). (1) Resolve needs a resolution and close a closure code by default (closure rules, editable per type: standard and custom fields; a custom field removed since is not asked for). (2) Open work warns (explicit confirmation, recorded with the items) for tasks, checklists and child incidents and blocks for approvals; "complete on close" off. (3) **Auto-close: never for a requester who was not told.** The waiting period (3 business days when switched on, 1–30) counts from when a channel actually told the requester of the resolution; off by default, and it cannot be switched on while no channel reaches requesters (product owner, 2026-10-28). Business days are Monday to Friday until WP-025's working calendars. (4) A requester cannot pick a closure code: their confirmation (and auto-close) closes with **the dedicated code "Confirmed by requester"** (seeded for every tenant, renamable) when the rules require a code and none was set, so reports tell technician closure from customer confirmation (product owner); when the rules need anything else the record lacks, the confirmation is recorded and the record stays resolved for a technician. (5) Reopen window 7 days (1–30); a requester reply within it reopens to in progress, after it starts a new record that follows the old one; when that new record cannot be created (a template that requires more), the reply stays on the closed record and history says so. (6) A requester reply resumes "awaiting requester" (per-status switch), never "awaiting third party". (7) Reopen clears the current resolution and closure code (history keeps them) so the next resolve asks again; **the resolve dialog then shows the earlier resolution with "Reuse"** (product owner).
