# D-187 (2026-11-24)

## Decision

**The Keycloak realm keeps undeclared user attributes for admins only
(`unmanagedAttributePolicy` = ADMIN_EDIT), set at every deploy.** Haider, the product owner,
chose option A through the coordinator (item 28), for WP-057 S5c: roles and support groups that
follow a person's identity-provider groups.

- A provider's groups reach SupportX in per-alias user attributes, written by the provider's
  mappers at each brokered sign-in (FORCE): `sx_groups_<alias>`, `sx_groups_seen_<alias>`,
  `sx_groups_overage_<alias>` and `sx_groups_hasgroups_<alias>`. SupportX reads, then clears,
  them at sign-in under a per-person lock.
- Keycloak 26 drops attributes the user profile doesn't declare. The `keycloak-identity` Job sets
  the realm's user profile to keep undeclared attributes, visible and editable by admins only, on
  every run, upgraded realms included.
- **Never ENABLED** (user-editable): a person could then write their own groups and SupportX
  would grant what they wrote. The Job corrects any other value; it is a security baseline, not
  an operator choice.

## Rationale

The attribute names depend on each tenant's provider alias, so they can't be declared ahead.
Option B was to declare each alias's attributes when a set-up is made and remove them when it is
deleted. That's more realm writes per set-up, more to keep in step across tenants on a shared
realm, and a dropped attribute if a declaration is ever missed. Option A is one realm setting,
the same for every installation, and the admin-only edit right keeps the attributes as
trustworthy as the declared ones. The identity account never holds manage-realm, so it can't
change the setting.
