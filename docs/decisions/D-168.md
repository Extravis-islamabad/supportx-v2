# D-168 (2026-11-13)

## Decision

**Security paths are code-owned by a separate reviewer account** (Haider, the product owner,
through the coordinator; lane B builds it).

1. **The reviewer account:** Haider creates a free GitHub account, `supportx-reviewer`, which lane
   B uses to approve security pull requests. Haider sets up its sign-in himself; no session,
   script or file ever handles the account's token or password.
2. **CODEOWNERS:** `.github/CODEOWNERS` names `@supportx-reviewer` for a tight, mostly file-level
   list: sign-in, sessions and tokens (identity BFF, session cipher and store, OIDC, API keys,
   MFA, SSO, password reset, service identities, break-glass and the sign-in policy, the
   Keycloak admin client); the policy layer,
   roles and the identity permission catalogue, with `main.py` and the module registry (see
   item 5 for routes and permissions); tenant isolation
   (`core/tenancy.py`, `core/database.py` where each transaction sets the tenant,
   `shared/db/rls.py`, `migrations/helpers.py` and `env.py`, the RLS guard and the migrations
   guard test); the route-permission and create-idempotency guard tests; internal TLS and routing
   (HTTPS) templates; settings, middleware, trusted proxies and rate limits; the shared
   crypto, egress and files packages; the audit and licensing modules; the secrets script, network
   policies, Keycloak files and identity tooling; `security.yml`, `.semgrep.yml` and `CODEOWNERS`
   itself. No test folders in general, no `ci.yml` or `cluster.yml`. Nothing else is owned: this
   **supersedes D-007's catch-all** (`* @devhat-pm`). Every lane pushes as that account, which
   can't approve its own PRs, so with code-owner review on every PR would block (the coordinator,
   for Haider, 2026-11-13).
3. **Required:** Haider turns on "Require review from code owners" in the `main` ruleset once the
   account exists.
4. **Migrations (option (b)):** CREATE/ALTER/DROP POLICY, GRANT and REVOKE reach migrations only
   through the owned `migrations/helpers.py`; `backend/tests/test_migration_policy_sql.py` fails
   on such SQL in any other migration. The merged migrations that already hold it are a fixed list
   in the test, as merged migrations are never edited (CLAUDE.md §6).
5. **Routes and permissions through a generated map (narrowing, Haider 2026-11-13 via the
   coordinator):** module `api/` folders and the modules' permission catalogues (`__init__.py`,
   `work_items/service/access.py`, `portal.py`) are **not** owned, since nearly every feature PR
   touches them. Instead `docs/security/route-permissions.md` is generated from code by
   `make route-permissions` (`backend/tooling/route_permissions.py`) and committed: every
   `/api/v1` route with its declared access (permissions, signed in or public) and the scopes each
   permission takes, plus every built-in role's permissions and scopes under both first-run
   answers. `backend/tests/test_route_permission_map.py` fails when the committed file is stale.
   The map, its generator and test, and the role matrix pin (`identity_access/tests/
   role_matrix.json`, `test_role_matrix.py`) are owned, so a new route, a changed route
   permission or a changed role default needs the security review; other feature PRs don't.

## Rationale

- One mistake in these files can let one tenant read another's data or let someone sign in who
  shouldn't. A required review by a named security reviewer, only on those paths, catches that
  without slowing every other pull request.
- Owning every migration would put nearly every work package behind the security review. Keeping
  the access SQL in owned helpers protects the part that matters with a plain, strict test.
- The same holds for routes: owning every `api/` folder and catalogue would put most feature PRs
  behind the review. The generated map changes only when access changes, so only those PRs wait.

## Affected docs

.github/CODEOWNERS, docs/security/route-permissions.md (generated), docs/dev-setup.md (Security code owners), docs/architecture/tenancy.md (Adding
a new tenant-scoped table), backend/tests/test_migration_policy_sql.py.
