# D-116 (2026-10-29)

## Decision

**WP-024 session 2 defaults: Microsoft 365 and Gmail mailboxes, attachments from mail** (**approved by the product owner via the coordinator 2026-10-29**, including no Gmail domain-wide delegation and the failing notice on by default but not required; builds on D-109; D-112 to D-115 are taken on other branches, so the number is rechecked against main at merge). (1) **The customer's own OAuth app per mailbox:** its IDs and its client secret or certificate are entered on Admin › Mail and sealed with the installation key ring (purpose `mailbox`), never returned or logged; on-prem mail never passes through an Extravis app (D-109 (2)). (2) **Sign-in models:** Microsoft 365 with application permission (no one signs in; the admin guide limits the app to the support mailboxes with RBAC for Applications) or delegated (signed in as the mailbox); Gmail delegated only. Domain-wide delegation is not offered (it reaches every mailbox). A Microsoft certificate is an RSA key and certificate in PEM; its expiry is read from it. (3) **Least scopes:** Graph `Mail.ReadWrite` (+ `offline_access` when delegated) and Gmail `gmail.modify`; never sending through these APIs, never full mailbox access. (4) **Consent:** PKCE; the state is random, stored only as a SHA-256 hash, used once, valid ten minutes and only for the admin who started it, and the browser must return to the same address; the account that signed in must be the mailbox itself; refresh tokens are sealed (purpose `mailbox_token`) and a rotated one is kept. (5) **Never silent:** a mailbox that starts failing, or fails for a new reason, notifies the people who hold `mailboxes.manage` (in the app and by e-mail, on by default, not "required" so the Status category stays a personal choice); an app secret or certificate is announced 14 days before it expires, once per expiry date; the mail page shows both. (6) **Attachments** go through WP-022's one upload path as the sender (owner check, size limit, blocked types, quota, encryption, scan). They are screened against the tenant's file rules before the record is made; refused files are named in the record's text with the reason, in the sender's language. Inline images are kept as attachments. Reply attachments go on the reply's conversation entry (lane A's `RequesterReply`), on the record until that lands. Object storage being down leaves the mail on the server for the next fetch. (7) **API:** host, port and user name become null for API mailboxes; listed as accepted breaks under D-109 (D-095). (8) **Not in session 2** (session 3): outgoing mail per mailbox (REQ-INT-053), delivery state of replies and resend (REQ-INC-059), the composer without mail (REQ-INC-060). **Session 3 additions** (plan ~/Desktop/wp-024-s3-plan.md, approved by the coordinator 2026-10-29 except (9)): (9) **Send as this mailbox** (approved by the product owner 2026-10-29): an admin opts in per mailbox; only then is the send scope asked for (`Mail.Send` on Microsoft 365, `gmail.send` on Gmail). Least privilege: on Microsoft 365 the app's send permission must be restricted to the opted-in mailboxes only (RBAC for Applications, or an application access policy), never tenant-wide send-as; on Gmail it is limited to the connected mailbox (its own sign-in). Without the opt-in, mail about a record goes from the tenant's default sender with Reply-To set to the mailbox it came through, so replies still thread. The set-up is in docs/guides/mail-oauth-apps.md. (10) **Waiting, never late, never silent:** an e-mail that cannot go out because outgoing mail is not set up waits; the reply shows "waiting" with its reason, and the admins see how many wait. After 7 days it fails with `not_sent_in_time`, visibly on the reply, and is never sent late. (11) **Delivery state on the reply** follows the e-mail to the requester: waiting, queued, retrying, sent, failed with the server's reason as a code; a late, older report never moves it back, and a sent reply never moves again (agreed with lane A). (12) **Resend:** anyone who may reply on the record; audited, needs the entry's version and an Idempotency-Key; only a failed reply can be resent, so a double click sends once; refused while mail is still not set up. (14) **Floods, replies included** (product owner, 2026-10-29): replies count towards the per-sender flood limit (10 messages an hour). Anything over it is held in the review queue, never dropped. The mailbox shows it as flooding until every such sender is back under the limit (it clears by itself, live), and the people who manage mailboxes get one notice per flood (`mailbox.mail_held`); no "recovered" notice. (13) **Split with lane A:** lane B builds the states, the engine, the resend port (`notifications.resend_entry`) and `GET /notifications/mail-status` (staff only, names only); lane A builds the timeline chips, the resend route and button, and the composer notice.
