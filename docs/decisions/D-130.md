# D-130 (2026-11-03)

## Decision

**AD/LDAP through Keycloak federation, with a separate federation account** (product owner,
2026-11-03, in lane B's session, option (a) of the WP-040 security design). In the product
owner's words: a separate `supportx-federation` Keycloak account with only manage-realm,
created only when an on-prem customer enables LDAP, never on SaaS; its secret in the secrets
store; every use audited. The existing identity account (`supportx-identity`, D-094) stays
limited.

How it is built (WP-040, D-118):
- **The account.** `supportx-federation` holds realm-management `manage-realm` only. The
  identity set-up step creates it only when its secret is configured; the Helm chart passes the
  secret only with `directory.ldap.enabled` and refuses that with `multiTenant`. Turning LDAP off
  switches the account off; the account is never deleted. Only the consumers worker holds the
  secret, never the API.
- **The guard.** It holds without branching on deployment mode (CLAUDE.md rule 5f):
  - the licence add-on `directory_federation` (in no edition, an add-on of on-prem licences);
  - the installation's `multi_tenant` off (the realm serves one tenant);
  - the federation account installed.
- **The connection.** LDAPS by default; StartTLS allowed; plain `ldap://` only by an explicit
  choice, recorded in the audit entry of every save. Read-only: SupportX never writes to the
  customer's directory. The bind password is sealed in the secrets store and never shown again.
- **Keycloak's side.** The worker writes one user-federation component per directory (named
  `supportx-<id>`) and exactly its mappers: email, names, department and site into
  `sx_department` and `sx_site`, Active Directory account control, and groups when a groups
  folder is set. It records `pending`, then `applied` or `failed` with a reason code, live on the
  screen. Every use of the account is audited (`directory.federation_applied`, `_failed`,
  `_removed`).
- **People.** Keycloak imports the directory (changes every 30 minutes, everyone daily, D-118
  defaults, editable). SupportX reads the users of that component on the same interval, through
  the Entra sync's engine and rules (source `ldap`): a person disabled in AD, or gone from it,
  is a leaver. An empty answer while SupportX still keeps people from that directory changes no
  one.
- **Tests.** A test-only image built from Debian's `slapd` (OpenLDAP Public Licence) on a
  debian-slim base pinned by digest, for the integration test.

## Rationale

The identity account manages users only and must not gain realm-wide rights. A user-federation
component needs manage-realm, so a second account limits that right to the installations that
asked for LDAP. Keycloak checking AD passwords at sign-in keeps passwords out of SupportX.
