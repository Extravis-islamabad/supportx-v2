# D-163 (2026-11-12)

## Decision

**HA installs on k3s run NodeLocal DNSCache, a DNS cache on every node** (Haider, the product
owner, through the coordinator; lane B builds it).

1. **The image is approved:** `registry.k8s.io/dns/k8s-dns-node-cache` (Apache-2.0, the
   Kubernetes project's own), pinned by digest in `values.yaml` (`images.nodeLocalDns`, 1.27.1).
   It is listed with the other images, so the air-gapped image list and the Zot mirror carry it
   (D-038).
2. **A cluster add-on, not part of the chart:** `deploy/k3s/node-local-dns.sh` installs it after
   `cluster-dns-ha.sh`, once per cluster and after every k3s upgrade, in transparent mode (the
   cache takes the kube-dns address on each node; no k3s or kubelet flag changes). It needs
   kube-proxy in iptables mode, k3s's default.
3. **The preflight requires it** for the HA profile: a ready cache on every schedulable node,
   kube-proxy not in ipvs mode, and, with the egress allow-list on, the cache's addresses in the
   policy (`networkPolicies.egress.dnsAddresses`).
4. **The node-loss tests hold it to account:** Valkey failover and the same session's write
   within 60 s (they were 90 s), and no sentinel enters TILT.

## Rationale

- With two CoreDNS copies a lost node's copy still stays behind the kube-dns Service for about
  20 s. Valkey's sentinels resolve hostnames synchronously, stall on it, and enter TILT, a fixed
  30 s pause: failover took about 50 s (Cluster runs 43153098860 and 43157246881). A cache on
  every node answers from memory and reaches CoreDNS over TCP, which fails fast on a dead copy.
- Transparent mode keeps pods' DNS settings as they are, so nothing in k3s or the chart's pods
  changes, and k3s's own CoreDNS settings still decide every answer.
