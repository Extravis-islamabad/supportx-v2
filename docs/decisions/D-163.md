# D-163 (2026-11-12)

## Decision

**The mobile app's debug build gets the web's dev-only quick sign-in** (the product owner,
2026-11-12: "do as it is done on the web").

1. The Sign in screen of a debug build (`__DEV__`) shows one button per Showcase Company persona,
   the same personas and labels as the web's `/dev/sign-in` (D-151). Release builds never show
   it.
2. A new endpoint `POST /api/v1/auth/dev/mobile/sign-in` signs the persona in exactly like the web
   one: same guards (the dev-only setting `SUPPORTX_DEV_QUICK_SIGN_IN`, a local address, the
   showcase tenant), Keycloak's password grant with the persona's second step, the normal session
   path and the `session.quick_sign_in` audit entry (client `mobile`). It returns the session ID
   in the body and never sets a cookie; the app keeps it like the one from the real sign-in
   (`X-SupportX-Session`, ADR-044).
3. Only the app may call it: the request must carry `X-SupportX-Client: mobile` and no `Origin`.
   A browser sends Origin on every POST and must ask first (CORS preflight) before sending that
   header, which the API never allows, so no web page can post there or read a session ID. Like
   the web endpoints, it is hidden from OpenAPI and answers 404 when anything does not hold.
4. ADR-044 is unchanged: the real mobile sign-in still returns only through the verified https
   link. This is a local-dev aid, because that link cannot be verified on `http://localhost`.

## Rationale

On the local stack the mobile sign-in stops in the browser: Android hands `/mobile/auth` to the
app only through a verified App Link, which needs an https host serving `.well-known` files. The
web already solved the same need for QA with D-151, so the app reuses that path and its safety
rules instead of adding a custom URL scheme (which ADR-044 rejected) or a public tunnel.
