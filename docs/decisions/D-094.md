# D-094 (2026-10-27)

## Decision

**WP-039 session 1 defaults** (built under D-089; each reversible). (1) **Service account `supportx-identity`**: client credentials only, exactly `manage-users`, `manage-identity-providers`, `manage-organizations`, `view-events` (least privilege, verified on Keycloak 26.8.1: no realm, client or master rights). Created by an upgrade step (chart Job per revision, `make keycloak-identity`), never in the realm import file; the same step turns login events on (7 days), raises the realm's SSO session to SupportX's longest (so SupportX's per-tenant timeouts decide) and declares the SSO attributes `sx_department`/`sx_site` in the user profile (admins only). (2) **Sessions per tenant and app** (Appendix A defaults and caps) apply to sessions begun after a change; signing in after a timed-out session asks for the password again (`prompt=login`). (3) **Deactivation ends sessions and live connections at once; Keycloak sessions are not ended** (one Keycloak user serves all of a person's tenants); ending Keycloak sessions comes with admin password and MFA resets. (4) **People creation on first sign-in**: on by default; off refuses unknown people ("contact your service desk"). (5) **Single sign-on**: up to 5 set-ups per tenant (Entra ID, Okta, Google, any OpenID Connect, SAML 2.0), each a Keycloak identity provider linked to the tenant's organization, created hidden; its email domains are routed to it on the organization (Keycloak 26.8 domain routing); public mail domains are refused, a domain of another organization is refused by Keycloak, two set-ups of a tenant never share a domain; the client secret lives only in Keycloak (write-only); SAML metadata is read by Keycloak's import endpoint, fetched by SupportX through a request-forgery-limited fetch (loopback only where `sso_fetch_allow_loopback` is set: dev and CI). Saving checks the connection: OIDC discovery, issuer and client authentication; SAML certificate dates. (6) **Test before switching on, in a private window**: Keycloak refuses to sign a second person in where the admin is signed in (and leaves a half-made account), so the screen gives a link; the test creates no SupportX session and no person; a refusal recorded by Keycloak is reported in plain words, and since a SAML signature failure is not recorded, the screen explains after a minute that the other window's error is the reason. Only a set-up tested since its last connection change can be switched on; an "on" set-up is switched off before its connection changes. (7) **Sending people of the domain straight to the provider** is off by default and applies only while on. (8) **Department and site from SSO** are applied when the person is created, matched by code or name, never created (D-089 D6; WP-021 has landed). (9) **Account linking**: Keycloak's default first sign-in flow (confirm, then prove the existing account) is kept; automatic linking is never configured (in a shared realm it would let one tenant's provider take over another tenant's user). **Open before tenants share a realm (SaaS):** email domains are claimed unverified; a proof of domain ownership must come first, or a tenant could claim another's domain and send its people to its own provider. On-prem with one tenant per installation (D-070) is not affected.

## Rationale

WP-039 session 1, built and checked against Keycloak 26.8.1.
