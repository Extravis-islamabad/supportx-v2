# D-179 (2026-11-20)

## Decision

**The asset availability route is a shared loan pool by design, and shows only the product, the
site name and when the units are busy: never which asset, its tag, who holds it, or any record
it serves.**

This is the coordinator's decision, given to Haider (the product owner) as an FYI. It is not
Haider's own words.

- `GET /api/v1/assets/availability` returns `product_id`, `product_name`, `site_name` and `busy`
  only. The asset's `id`, `name`, `tag`, `site_id` and `held` are removed; these are accepted
  breaks in `docs/architecture/openapi-accepted-breaks.json` (D-095).
- It is not narrowed by the reader's asset scope: the pool is shared, so everyone who may ask sees
  the same thing, and that thing names no asset or person.

## Rationale

- The asset-scope fix (#558) found asset registers that ignored a site-scoped reader's scope.
  Availability was the one register that is meant to be shared, so the fix keeps it shared and
  removes everything in it that could identify an asset or a person.
- No screen uses this route today; it has only its api-client hook. Booking is unaffected: the
  portal books through `GET /assets/bookable` (unchanged) and `POST /assets/bookings` by asset ID,
  and staff book from an asset's own (scoped) record.
- `/assets/bookable` still shows bookable assets' tags and names to every signed-in portal
  person, as the existing loan-pool design. Booking by product and site with the server choosing
  the unit would be a separate change to the portal flow.

## Affected docs

`docs/architecture/openapi-accepted-breaks.json`; `backend/app/modules/assets/api/stock.py`
(`AssetPoolSlotOut`, the route's docstring).
