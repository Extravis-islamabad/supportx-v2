# D-169 (2026-11-13)

## Decision

**Staging runs on the spare laptop (Ubuntu Server), pull-based** (Haider, the product owner,
through the coordinator; lane B writes the runbook and the nightly job).

1. **Pull, never push.** The laptop is never a CI runner and accepts no inbound webhook. A
   nightly job on the laptop pulls `main` into a checkout used only by that job, builds the images
   there, and installs or upgrades SupportX, then runs the Helm tests and a smoke check.
2. **It doubles as the offline-installer rehearsal.** The nightly sequence is the one an
   air-gapped install follows. What a true offline rehearsal still needs (an image bundle or a Zot
   mirror, the k3s air-gap install, the signed installer: D-038, WP-014c) is listed in the
   runbook.
3. **Nothing open beyond what Haider needs.** SSH and the app's HTTPS port from the local
   network only, nothing from the internet.
4. **Demo data only.** Seeded demo tenants, never customer or production data.
5. **Error tracking on by default** there once GlitchTip lands (D-167).

## Rationale

- A machine that only pulls has no inbound attack surface, needs no CI credentials and can't be
  used to run anyone else's code.
- Installing from `main` every night proves the install and upgrade path continuously, which is
  what the offline installer must do on a customer's machine.
- Images tagged by commit let `helm rollback` bring back the previous images as well as the
  previous settings; the first install is done by hand, because an automatic first install that
  failed would be rolled back by uninstalling, which deletes the database cluster.
