# D-132 (2026-11-04)

## Decision

**WP-030 D7: approving by e-mail link** (product owner, through the coordinator, 2026-11-04;
replaces the interim default "sign-in required").

1. **One-time links are allowed by default.** An approver can approve or reject from the e-mail
   without signing in.
2. **Opening a link never decides.** It shows a confirmation page with the request's summary; the
   approver presses Approve or Reject (mail scanners pre-open links).
3. **Single use, 72 hours, bound to that approver, every use audited** (refusals too).
4. **A rejection needs a reason** (REQ-SR-028).
5. **"Require sign-in for approvals"**: a tenant setting, **off** by default, for customers who
   want the approver signed in; with it on, a link only works for its signed-in recipient.

6. **Links are never stored in full and never logged** (product owner's addition, approving
   lane B's precondition): a rendered e-mail is stored with the token removed. Its bodies hold a
   marker where the link goes and the message keeps only who, which action and which object; the
   mail sender makes the token at send and puts it in the outgoing copy alone. No stored body,
   delivery row, outbox event, audit entry or log line (the mail send log, access logs) holds a
   token, and none reaches a Referer (the token travels in the URL fragment). A retry or a
   resend makes a fresh link and revokes the one that never left.

Lane B's five conditions for signed action links stay in force (REQ-NTF-024: GET never acts; a
random 32-byte token kept only as its SHA-256 in a tenant table with RLS, bound to recipient,
action, object and version, single use, short expiry; the token never in logs or a Referer; every
use audited as the recipient, the page rate-limited; a policy check at use time). Lane B's
precondition for links that work without sign-in is met by point 6: no stored body ever holds a
token, so there is nothing to clear after a send or a failure.

## Rationale

Approvers (managers, budget holders) often decide from their phone's mail; requiring a sign-in
there was the main obstacle in the parity notes (file 02, question 3). The confirmation page keeps
pre-opening scanners from deciding; binding, single use, the expiry and the audit keep a forwarded
or leaked link from doing more than its approver could; the setting serves customers whose policy
asks for a signed-in approver.
