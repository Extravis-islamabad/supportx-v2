# D-166 (2026-11-12)

## Decision

**The HA profile runs the bundled SeaweedFS with SeaweedFS's own replication** (Haider, the
product owner, through the coordinator; lane B builds it). It replaces decision b of
2026-11-12, under which HA installs had to bring their own S3-compatible store.

1. **Topology, HA profile only** (`objectStorage.seaweedfs.ha`, on in `values-ha.yaml`): three
   masters (raft), three volume servers and two filers running the S3 gateway, each on its own
   node, behind the unchanged `<release>-seaweedfs:8333` Service. Single-node and dev keep the
   single `weed server` pod as it is.
2. **Two copies of every file** (default replication `001`, a values switch; `002` allowed), the
   leader master re-making missing copies every 17 minutes (`volume.fix.replication`).
3. **The filers' metadata in the release's CloudNativePG cluster**: a separate database
   (`seaweedfs_filer`) and a separate least-privilege role that can reach no other database,
   so it is in the same backups and the same restore. Its password lives in a Secret of its own.
4. **External object storage stays supported** (a MinIO cluster, NetApp, Ceph RGW, cloud S3):
   with `objectStorage.mode: external` none of this is installed.
5. **Proof in CI**: the HA preflight checks the masters' and volume servers' spread and the
   replication; the Cluster workflow's HA job stops the node with the raft leader and a volume
   server and requires every attachment to read and write within 60 s and every volume to get
   its copies back; the restore drill checks the filers' database comes back.
6. **Moving a single-copy install to HA is a documented rclone copy** with `rclone check`, not
   automated.

## Rationale

- Customers on the HA profile without their own S3 cluster had no highly available home for
  attachments: the single SeaweedFS pod's node was a single point of failure.
- SeaweedFS is already bundled, pinned and approved (ADR-012, D-076); its own replication needs
  no new image or dependency, and keeps on-prem and air-gapped installs self-contained.
- Keeping the file tree in the database the release already backs up means one backup and one
  restore cover it, rather than another store to protect.
- Replication protects against a lost server, not against a deleted or overwritten file: the
  file-store backup (audit gap #1) is still needed.
