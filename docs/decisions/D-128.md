# D-128 (2026-11-04)

## Decision

**The public API: API keys, scopes and the contract's security** (WP-041; plan approved by the
coordinator 2026-11-03, key design approved by the product owner as security design).

- **Key format:** `sxk_<tenant>_<key id>_<secret>`. The tenant and key IDs are UUIDs in lowercase
  Crockford base32; the secret is 32 random bytes in base64url. The tenant comes first, so the
  API sets the tenant and finds the key under row-level security, with no lookup across tenants.
  The pattern is public (docs/api/keys.md) so secret scanners find leaked keys; `.gitleaks.toml`
  carries it, and the security workflow proves a sample key is caught by that rule.
- **Storage:** only an HMAC-SHA-256 of the secret, bound to the key ID, under a server key kept
  outside the database (`SUPPORTX_API_KEY_SECRET`, else derived from the session secret). A leaked
  database alone cannot test guesses. The screen keeps the last four characters.
- **Shown once:** the create answer carries the whole key. It is never stored, not even in the
  idempotency store: a retried create with the same Idempotency-Key answers without the key text,
  and the screen says to revoke it and make a new one.
- **Scopes:** `<area>:read` and `<area>:write` per area of the permission catalogue (`view`,
  `read`, `list`, `search` and `export` actions are read). A key does only what its scopes cover
  **and** what its owner may do now: the policy layer narrows the owner's live grants, so a
  role change applies to the key at once. A missing scope answers 403 `api_scope_missing`,
  naming a scope the key lacks.
- **Owners:** your own keys when the tenant allows it (`people_may_create_keys`, off by default);
  `api_keys.manage` for keys of service identities and every key.
- **Expiry:** 90 days by default, at most a year. Non-expiring keys only when the tenant allows
  them (`allow_non_expiring_keys`, off by default).
- **IP allowlist:** optional, per key. Another address is refused and audited.
- **Browser-only routes:** a person's own session, profile, realtime tokens and the key screens
  themselves refuse keys (`api_key_not_allowed`): a key never makes keys.
- **Audit and events:** made, revoked, refused and rule changes are audited. Made and revoked go
  through the outbox (`identity_access.api_key.changed`, owner ID only) and reach key managers'
  list and the owner's own channel live.
- **Contract:** every operation in the OpenAPI document names the scope a key needs (`x-scopes`)
  or says keys may not use it (`x-api-key: false`), under the `ApiKey` and `BrowserSession`
  security schemes. An oversized page size is reduced to the maximum and flagged with
  `X-Page-Size-Capped`, never refused. `make api-errors` lists the error codes with their
  English text.
- **Screens:** Admin › API keys (every key, the two tenant rules for whoever may change sign-in
  settings) and My profile › API keys (one's own, when allowed).
- **D-095 stays as it is until the pilot:** changes an approved decision requires are still listed
  in `docs/architecture/openapi-accepted-breaks.json`.

## Rationale

Integrations need a credential that is not a person's browser session, can be limited to what an
integration does, expires, and can be revoked at once. Binding the key to its owner's live
permissions means a key can never outlive or exceed the person or service identity behind it.
